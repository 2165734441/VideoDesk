## 要一起提供什么

- **同一台电脑上的智能体**：提供本文，告诉它项目位于 `E:\VideoDesk`。这是从 C 盘迁到 E 盘后的实际项目目录；旧 C 盘路径为兼容入口。不要让它重复搬迁、清理项目或重新打包。
- **其他电脑上的智能体**：提供本文及 `release/VideoDesk-2.7.0-Windows-x64.exe`；需要测试手机时再提供 `release/VideoDesk-Android-1.0.0.apk`。EXE 自带运行环境，黑盒测试不要求先装 Python 或 Node.js。
- **需要源码审查或运行源码测试**：另外提供当前源码及 `tests/`、`docs/`。不要直接发送整个工作目录；排除 `.local/`、`.git/`、虚拟环境、浏览器资料、Cookie、密钥、Android 签名文件、模型、用户素材、私人日志及真实任务库。当前 `package_share.py` 的命名仍是旧版本，不能未经检查就把它的输出当作 2.7.0 源码包。
- **真实抖音与手机测试**：准备可公开访问的直播间／主播主页／分享链接，以及允许用于测试的 Android 手机。登录、验证码、USB 安装及录屏授权由用户本人完成，不发送账号密码、Cookie 或会话 token。
- 最后让测试智能体回传：`BUG-REPORT.md`、`TEST-MATRIX.csv`、`repro/`，可以一起压缩成一个测试结果包。

### 2. 隔离测试，保护现有任务和手机

- 使用独立测试数据目录、输出目录和合成素材。开始前创建几个带已知 SHA256 的“原片／用户新增文件／共享文件”作为保护哨兵，验证清理、取消和重试不误删它们。
- 不要操作用户正在运行的工作台、正式任务库或现有录制。不能仅因为看见 `127.0.0.1` 页面就认为它是你的测试实例。
- 启动器支持 `--home <绝对路径>`，但这只隔离应用资料，**默认素材目录仍可能指向用户文档中的“映格素材”**。执行任何生成、下载或清理操作之前，必须在测试实例中确认输出目录已改到专用 QA 目录。
- 正常启动还可能创建／更新桌面入口。完整安装、托盘、修复、升级和长时间测试优先在虚拟机或独立 Windows 测试账户中完成，避免覆盖用户入口。
- 短时发布包冒烟可在独立目录使用 `--self-test --home <QA绝对路径> --report <报告绝对路径> --stop-file <停止标记绝对路径>`。该模式最长约 10 分钟，停止标记存在时结束；它的正常超时退出不能算崩溃，也不适合长时录播。先清除你自己上次留下的停止标记，再启动。不要删其他目录中的文件。
- 测试服务地址从该实例的 `data/server.json` 或启动报告读取，不要固定使用开发者机器上曾出现的 7485、7825、7826 等端口。
- 手机连接、APK 覆盖安装、ADB reverse 会影响当前手机的配对。操作前检查是否正在录制，优先使用测试手机／模拟器；需要使用用户手机时先说明具体影响。不要清空手机数据或卸载正式应用来解决签名问题。
- Android 录屏、USB 安装、通知读取和跳转抖音等系统确认由用户完成。需要人工操作时提出具体要求，继续做不依赖它的测试；不能绕过授权，也不能在未获得授权时填 PASS。
- 不修改系统服务、防火墙、系统 PATH 或全局代理来掩盖问题。仅在自己的进程或测试目录设置必要环境变量，并记录变更。

### 3. 测试顺序与重点

先做启动冒烟，再验证 A、B、C 三组用户直接反馈的链路，之后测试翻译、性能和历史回归。每个区域至少记录已执行的正常路径、一个失败路径和相关边界；无条件执行时写清具体阻碍。用例数量由真实覆盖决定，不为了凑数量重复拆分。

#### A. 关注列表数量、主播添加与身份识别【最高优先级】

1. 人工查看同一账号的关注数量与可见列表，再执行导入，记录账号、时间、分页数、原始条目数、去重后数量、界面显示的总数和完整性提示。平台页面截图需隐藏个人信息。
2. 覆盖多页、重复页／重复条目、中断后继续、部分页失败、登录失效、换号后重新导入，以及已删除／不可见账号。检查换号是否混入上个账号的数据。
3. 数量不一致时，核对是否明确展示“已读取／已知总数／未读取差额／完整性未确认”，而不是把部分列表宣称完整。平台总数不能直接当成当前可读取的条目数。
4. 分别测试直播间链接、主播主页链接、短分享链接、含文字的分享内容、前后空格、非法链接、非抖音链接、不开播主播。记录每类输入最终解析到的身份和错误提示。
5. 备注留空应能添加；备注用于识别列表项，可以编辑。仅凭昵称不能唯一定位主播，检查界面是否说明如何选择已导入关注项或提供链接。
6. 从关注列表选择主播后，不应再强制输入同一直播间链接。相同主播的不同合法链接应按稳定身份去重，同名的不同主播不能合并。
7. 检查公开直播间标识 webRID、secUid、实际 room ID 的用途是否混淆；19 位实际 room ID 必须保持精确字符串，不能因 JavaScript 数值精度改变最后几位。证据中列出原始值与每一层传递值。

#### B. 电脑抖音直播录播与回放【最高优先级】

1. 真实测试一个正在开播的直播间：添加→检测开播→开始录制→文件持续增长→停止并封装→界面找到回放→完整播放、拖动和检查音轨。单纯收到 HTTP 200 或生成非空文件不算录制成功。
2. 测试未开播、下播后重开、链接失效、登录过期、限流／验证页面、网络断开与恢复；不能把“无法确认状态”误报为“未开播”或“已开播”。
3. 在硬件和公开直播源允许时测试多主播并行：默认并发 4、超出并发后的排队、调到 1 与上限 8、停止其中一路后的队列释放。同一主播重复操作不得产生失控的重复录制。
4. 测试定时录制、跨午夜时段、分段保存、磁盘空间不足、不可写目录、手动取消、服务退出与重启后的状态恢复。空间不足只能在测试卷／小型测试容器中模拟，不能填满用户实际磁盘。
5. 校验录制文件的容器、时长、帧、音轨及实际可解码性，特别关注截断 MKV/TS、缺失尾段和“录制失败却显示成功”。受限文件可标记部分成功，但不能假报完整成功。
6. 如果平台返回 403/429/444、要求登录或安全验证，分别记录平台响应、手工浏览器能否访问、程序如何呈现和恢复。暂时无法获取流不等于已证明产品缺陷；程序崩溃、误报、死循环或无法恢复仍需单独分析。

#### C. Android 手机检测、通知和电脑／手机录制联动【最高优先级】

1. 验证 APK 安装／更新、USB 连接、断开与重连、认证桥接、电脑显示的连接状态。未认证请求应被拒绝，未连接时不能显示已成功下发。
2. 从电脑同步多个主播到手机；测试手机分享添加主播、重复同步、备注与身份对应，以及离线保存后重新连接。不要把真实凭据写入证据。
3. 手机前台轮询：已开播、未开播、未知页面、加载缓慢、重定向、短链接、主页、多个主播切换。特别检查旧页面异步回调是否错误更新当前主播状态。
4. 检查页面中被拆分／转义的 RSC 数据、19 位 room ID、相邻或推荐主播信息，确认识别的是目标主播。真实页面证据可以脱敏摘取最小结构，避免保存完整登录页面。
5. 手机发现开播后，电脑应收到对应主播事件，并可选择“电脑录制／手机录制／忽略”。三种操作分别验证实际行为、重复点击、迟到事件与失效事件。
6. 选择手机录制：解析准确的真实 room ID→系统录屏确认选择整个屏幕→开始录制→打开原生抖音对应直播间。确认没有停留在 WebView、错误主播或空白页。拒绝跳转、未装抖音和解析失败应有明确反馈与可行的手动路径。
7. 分别从手机按钮、系统录制通知、电脑停止录制；检查停止确认与真实停止是否一致，文件能否正常封装。重点测试“解析过程中停止”“等待授权时停止”“授权后立即停止”，不能在停止之后又延迟开始录制。
8. 测试重复开始、切换主播、手机后台／锁屏／返回前台、USB 中途拔出、电脑退出、应用被系统回收后的状态与文件完整性。记录电池策略、屏幕状态及权限，避免把环境差异写成笼统结论。
9. 检查 `Movies/VideoDesk` 中的 MP4、手机回放入口、音画同步和内部音频。需同时检查文件音轨、实际能否听到声音以及测试时抖音本身是否有声；不能只看存在 AAC 轨就声称音频正常。
10. 手机只有一套屏幕采集，不能同时独立录制多名主播；录制期间轮询其他主播应暂停。检查界面是否清楚反馈，电脑端多路录制不应受此限制。
11. 有通知权限时验证抖音开播通知入口；不凭同名通知直接认定目标主播开播。拒绝／撤销权限、无抖音通知和重复通知的降级行为均需记录。

#### D. 英文视频→中文字幕与中文配音

1. 用可公开再分发或合成的短英文样例完成识别→翻译→编辑→双语字幕→中文配音→成片，保存样例 SHA256、参数和中间结果。
2. 核对英文在上、中文在下，字幕的时间轴、换行、长句、标点、中文字体、非 UTF-8 字幕的提示、视频边缘可读性与音画同步。
3. 检查中文配音确实生成并进入输出音轨；记录声音是否可懂、漏句、重句、越界、截断、长句导致的错位，以及原声／背景音保留选项的实际效果。
4. 编辑识别和翻译后重新合成，确认结果使用新内容；取消、失败重试、批处理与重复运行不应混用其他任务的音频／字幕或覆盖原片。
5. 测试无声视频、无字幕、极短视频、较长视频、可变帧率、竖屏、中文／空格路径、缺失模型、组件安装失败、模型下载中断及断网。
6. 默认本地流程不应悄悄将媒体发送到云端。若主动选择云服务，检查配置与用户确认、错误反馈、凭据保护及恢复；不使用他人的付费密钥进行测试。

#### E. CPU／GPU 加速与回退

1. 记录实际硬件和组件，区分“支持／已选择／实际使用”。对语音、翻译、配音、视频编码分别观察实际后端；有显卡不代表每个步骤都使用显卡。
2. 比较同一文件、同一参数、同一模型的 CPU 与可用 GPU 流程，分开记录首次下载、首次加载、后续运行、各阶段和总耗时，附输出质量核验。两种模式均至少完成一次有效运行才给出直接速度比较；能重复 3 次时报告中位数及每次耗时。
3. 测试无独显、显卡不可用、显存不足、硬件编码器失败时的提示与 CPU 回退。只在独立测试进程中模拟故障，不卸载用户驱动。
4. CPU 回退应能产出可用视频，不应显示 GPU 已启用；性能档位不得暗中减少用户要求的采样、识别或字幕内容。直播直接存流通常不需要 GPU，不能以显卡利用率低判定这一路加速失效。
5. 关注 Windows 上平台信息查询、科学计算库导入、FFmpeg 和浏览器启动的超时／挂起。产品已有 `integrations.runtime_support.configure_platform()` 启动兼容处理；可以验证真实调用路径，但不可通过全局改系统或伪造硬件结果使测试通过。

#### F. 历史核心功能与数据保护

覆盖本地文件、拖放、多文件／文件夹、坏文件不影响其他任务、等待重选来源、取消／重试、抽帧、OCR、ASR、分镜、片段导出、拼图长图、照片去重、AI 素材包、CLI 与界面状态一致性。

重点回归：

- 长路径、中文／空格／逗号文件名、零字节与损坏媒体、输出目录不存在或只读。
- 字幕和片段边界、最后不足一段、进度与任务实际完成状态。
- 清理／回收只处理可确认归属的生成副本；保留原片、用户新增或修改的文件、被其他任务共享的文件。统计数量和实际处理一致，失败不能计作删除成功。
- 模型／运行组件安装失败、中断、重试、离线包损坏及恶意路径条目；仅在测试目录使用无害样例验证路径穿越防护。
- 关闭网页、重开网页、托盘退出、重新启动、修复和升级后的任务与设置保留。升级破坏性测试仅对虚拟机里的合成旧数据做快照后进行。
- 导出与诊断不泄露 Cookie、Authorization、session token、浏览器资料或 API 密钥。检查边界时只请求测试应用及自建本机服务，不扫描外部系统。

### 4. 已知限制及判定边界

这些属于当前设计或平台约束，先验证说明是否准确，再判断是否存在额外缺陷：

- 手机每次新建录屏会话可能要求 Android 本人授权；后台收到通知不能替用户自动同意录屏。
- 单台手机一次录一路屏幕，录制时暂停切换主播监测；多主播并行主要由电脑完成。
- 手机网页轮询需要保持前台，Android／vivo 省电策略可能冻结后台；需记录实际状态反馈与恢复是否正确。
- 当前电脑通信依赖 USB 连接和 ADB reverse，不承诺拔线后通过互联网继续控制。
- 手机录制保存手机本地，不自动上传电脑。声音受 Android 内部音频采集规则、来源应用和音量状态影响。
- 昵称是备注或选择提示，不是唯一身份。平台关注总数可能包含不可见／失效条目，工具不能保证读取平台未公开的数据；但必须如实显示完整性。
- 真实平台可能要求人工登录、验证或限流等待。测试不得绕过平台验证。

限制不能解释的误报、数据丢失、错误主播、无法停止、状态永久不恢复或界面误导仍可能是真实 Bug。按证据描述，不用“已知限制”笼统带过。

### 5. 源码测试与证据要求

源码环境先阅读 `docs/BUILD.md`，确认依赖和隔离路径。以下命令只能在源码根目录、你的测试环境执行：

```powershell
python -m unittest discover -s tests -p "test_*.py"
node --test tests/test_dedup_ui.mjs tests/test_progress_ui.mjs tests/test_sheet_limit.mjs tests/test_phone_detector.mjs
```

记录退出码、原始输出和收集到的实际用例数。失败后先判断缺陷、缺少依赖还是测试环境问题；不要先改断言、跳过用例或修改产品再宣称原版通过。

DSH 集成测试需要 `VIDEO_DESK_URL`、`VIDEO_DESK_TEST_VIDEO`、`VIDEO_DESK_TEST_OUTPUT`，具体按 `docs/BUILD.md` 设置到隔离实例与样例。缺少前置条件造成的跳过必须披露。不要不加检查地运行所有 `scripts/verify_*.py`，部分脚本依赖特定构建或会创建／写入测试数据。

自动化测试不能替代发布包安装、真实直播、实际音视频解码和真机授权链路。没有手机、显卡、登录条件或网络时，清楚列出未覆盖部分，继续完成其余可执行测试。

### 6. 必须交付的文件

#### `BUG-REPORT.md`

按以下顺序组织：真实复现缺陷→已验证项目→失败用例与 Bug 对照→代码审查候选→未测试项目→环境阻碍→已知限制→复现命令→修复优先级→测试结束状态。

每个实际缺陷至少包含：

- 编号 `VD27-001` 起、标题、严重性及理由；是否阻断主要功能、造成误删／泄露或有可靠绕过。
- 测试的 EXE／APK SHA256、环境、样例 SHA256、输入参数与前置条件。
- 最短复现步骤、预期结果、实际结果；复现次数写成“失败次数／尝试次数”。通常至少复现 2 次，间歇性问题如实记录，破坏性问题不强行重复。
- 时间戳、截图／录像／日志／JSON 证据的相对路径；必要时包含最小脚本及样例生成方法。
- 影响、绕过方法、修复建议和可以客观判断的验收条件。
- 有源码时列出准确的文件、行号、调用路径，并区分已证实根因与推测；黑盒测试没有源码就写明，不编造行号。

只读代码猜测的问题进入“代码审查候选”，不能混入已复现 Bug。多个失败用例由同一根因导致时合并 Bug，保留全部用例编号。

#### `TEST-MATRIX.csv`

UTF-8 编码，至少含以下列，字段中有逗号或换行时正确引用：

```text
case_id,module,title,artifact_sha256,environment,preconditions,input,steps,expected,actual,status,bug_id,evidence,attempts,reason
```

状态仅使用：`PASS`、`FAIL`、`BLOCKED`、`SKIPPED`。`FAIL` 表示已观察到产品行为不符合明确预期；环境或权限不具备用 `BLOCKED`；未执行用 `SKIPPED`，并写明原因。没有执行不能填 PASS。

报告提供总数及四类数量，必须与 CSV 行数、Bug 编号映射和证据一致，不设预期 Bug 数或通过率。

#### `repro/`

建议结构：

```text
repro/
  README.md             # 顺序、依赖、运行与停止方法
  environment.json      # 脱敏环境和实际构建标识
  scripts/              # 最小复现脚本
  samples/              # 小型合成样例或生成脚本
  evidence/             # 结构化响应、截图、最小录像等
  logs/                 # 脱敏日志
```

优先提供可复现的小型合成样例；大文件可提供生成方法、哈希与关键片段。截图和音视频应只保留证明问题所必需的范围。

交付前脱敏用户名／私人目录、个人关注列表、账号、Cookie、会话 token、Authorization、桥接认证凭据、API 密钥等。用程序扫描最终报告、CSV、脚本及日志中的敏感字段，再人工检查截图和媒体；扫描结果与方式一并说明，不声称扫描能保证绝对无泄露。

不得打包虚拟环境、浏览器用户目录、模型、整个应用数据库、签名 keystore 或签名密码。停止自己启动的测试实例与录制，恢复自己改变的测试配置，保留复现证据；不要停止用户原有服务或删除其素材。

### 7. 最终回复格式

用中文直接说明测试了哪个构建，实际发现多少个已复现 Bug，最严重的问题是什么，四类用例各多少，以及还有哪些关键功能因环境不能确认。附上三个交付物的路径。

若未发现缺陷，应写“在已执行范围内未发现可复现缺陷”，列清未测试范围，不能声称软件没有 Bug。不要只交测试计划、泛泛建议或读取旧报告后的总结。
