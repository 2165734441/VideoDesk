## BUG-01（手机只显示 5 位主播）— 结论修正：不是数据丢失，是卡片太高 + 没有滚动提示

**复核方式**：在真机上用 `adb shell input swipe 720 2600 720 900 400` 上滑后重新 dump，8 位主播全部在列表里（辉辉 呀、喜哥、泽凯都出现在滑动后的节点里）。`anchors` 一直是 8 条，`render()` 也确实循环了 8 次——`/v1/config`、`acceptConfig()`、`render()` 三层数据链路没有问题，`lastSignature` 提前 return 也没触发（8≠5 时必然重绘）。

**误判根源**：`uiautomator dump` 只输出 ScrollView **可见区域**内的子节点，第 6~8 张卡片被滚出视口，所以 XML 里"只有 5 张卡片"。当时每张卡片约 600px（170dp），1440×3200 的屏幕一屏只能放下 4~5 张，且界面没有任何"还有更多"的提示，看起来就像数据缺了 3 条。

**改动**（`mobile/src/org/videodesk/mobile/MainActivity.java`）
- 卡片紧凑化：卡内边距 14dp→7dp、卡片间距 14dp→7dp、标题 16→15sp、状态行 13→12sp、按钮新增 `compact()`（去掉 Android 默认的 48dp 最小高度、内边距 6dp、字号 12sp）。实测单卡从 ~600px 降到 ~436px，一屏可见 6 张。
- 列表底部常驻提示 `共 N 位主播 · 列表可上下滑动`（列表页脚、按钮栏上方，随数量实时更新）。这就是"缺 3 位"的可见性补偿。
- 版本升到 1.3.5 / versionCode 13。

**验证记录**：安装 1.3.5 后 dump → `共 8 位主播 · 列表可上下滑动 | [56,2884][1384,2980]`，可见 6 张卡片，上滑后 8 张齐全。

> 复验提示：以后判断"列表少了几条"必须滑动后再 dump，或直接看 `anchors.length()`；单纯数 dump 里的卡片数会误判。

## BUG-02（已录到片段却报 error + "没有取得直播流"）— 已修

`integrations/live.py` `record()` 的取流异常分支原来无条件抛错：只要 `not automatic` 或连续失败 5 次，就把任务置 error，完全没看 `segments` 里是否已经躺着录制成功的片段。

现在：**只要已经有成功片段，就按"直播已结束"收尾**
- 手动录制：连续失败 2 次后退出循环 → `status=done`、`已保存 N 段回放`；中途重连时任务保持 `recording`，消息为"…；正在重连，已有片段保留"。
- 自动监控：保留 5 次重试（短暂抖动不该结束一场还在播的直播），5 次仍失败且有片段 → `done` 而不是 error。
- 一个片段都没取到时，仍按原样报错（不掩盖真实失败）。

**回归测试**：`tests/test_bugfix1119.py::LiveEnding`（4 条，含"已有片段→done 且 replay.json 有 1 段"、"紧急抖动仍继续录"、"零片段→error"）。

## BUG-03（检测中/失败状态的主播无法删除）— 已修

原来路由把 `key in manager.active or key in manager.pending` 一律当"正在录制"，于是"未开播/检测失败"的主播永远删不掉。

现在新增 `Manager.remove(key)`（路由变薄壳）：
- 只有 `runtime.state == 'recording'` 或任务 `status == 'recording'`（真正在写盘）才 409；
- 其他情况（排队/检测中/失败/等待）先 `EVENTS[jid].set()` 取消这次检查、清掉 active/pending/next_check，再删主播，不再要求先 stop。

**实测**：`POST /api/live/anchors` 新建主播 `573d458f65c5`（假房间号，必然检测失败）→ `DELETE /api/live/anchors/573d458f65c5` 返回 **200**，列表无残留。修复前同场景是 409。

**回归测试**：`AnchorDelete` 三条（检测中可删并取消任务 / 录制中 409 / 手机录制中 409）。
